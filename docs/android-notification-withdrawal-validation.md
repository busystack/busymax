backend harness, with two independent SQLite connections to one durable file.

still-relevant event alarm at 08:55. A Completer holds its first registration.
Event reminders are disabled before release. Cancellation #1 succeeds; exactly

## Correction and coverage

`android_notifications.dart` uses `_isPendingReplacement` consistently for the
four delivery/dismissal inferences and when retaining a replacement decision.
It recognizes both forms generated by the reconciler: `replacing:…` and
`withdrawing:replacing:…`. Withdrawal's outer cleanup obligation therefore cannot
erase the known-pending fact or cause another replacement wrapper to hide it.
Cleanup is retried before registering the retained ID/generation. Real active
evidence still takes precedence; ordinary ambiguous or consumed registrations
retain their duplicate-suppression behavior.

The seven-case service matrix checks the persisted wrapped checkpoint and
cancellation sequence. Known-pending cases retain null history, native
ID/generation/payload and exactly one replacement through repeated reconciliation
and inspection recovery; later actual delivery is then observed. Active and
consumed controls remain consumed. Source event cancellation/deletion fields
remain false.
The existing displayed-post, privacy and cancellation-recovery tests remain
enabled.

Current-session logs and native evidence are retained locally under ignored
`build/notification-withdrawal/`; earlier test counts are not adopted as new
results. The targeted pre-fix run had 3 passes and 2 intentional failures.
After the wrapper repair, the complete Android reconciliation file passed 55
tests and the broader batch passed 357. The expanded final matrix adds channel
restoration with inspection available/unavailable; the final affected batch
passed 359, including all 57 reconciliation cases. Counts overlap and are not
added.

Inspection of the remaining state writes confirmed one adjacent loss of the same
fact: a temporarily blocked channel overwrote the marker with `blocked`. The
expanded regression had 6 passes and 1 failure before that correction: available
inspection recovered, but unavailable inspection falsely recorded submission on
channel restoration. The blocked-delivery branch now retains the known-pending
marker, keeps readiness false and makes no registration while blocked. Restoring
native capability then registers once without consuming history. This changes
neither the app preference nor any OS/channel setting.

successfully uninstalled; the regular package's installation state was unchanged.
The final APK repeated both physical cases after the channel-state refinement.

Host SQLite inspection independently verified null delivery/dismissal/expiry
history, the retained mapping and unchanged source fields in both final captures

The fixed application clock was 15 minutes ahead of actual time so a real future

phone's system clock, timezone, OS permissions and channel choices were not
changed. This checks native registration/cleanup and retry state; it does not
establish real-world OEM alarm delay, banner/sound or lock-screen presentation.
The controls for actual active evidence, genuinely consumed posts and temporary

the physical check did not change OS channel settings.
